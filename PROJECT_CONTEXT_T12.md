# Doboz T12 — Project Context

## Purpose

Alternative firmware for the Doboz T12 Eurorack module. The current firmware is a native C++ Pico SDK project for the RP2040. It replaces the original Doboz firmware while preserving the hardware interface.

## Touch controller

The touch controller is an NXP MPR121. Twelve electrodes are used for the twelve capacitive pads. The firmware reads:

- touch bitmask;
- filtered capacitance value for each electrode.

The filtered capacitance is used for the Auxiliary CV `CAP SENSE` mode and for the brightness of the corresponding RGB pad LED. A future calibration should store per-pad idle/baseline and touch range values.

## OLED

OLED is monochrome SPI, 128×64. The display has a two-column horizontal offset correction in `display.cpp`; preserve this when changing rendering.

The firmware uses a custom 5×7 bitmap glyph set in `sequencer/src/graphics.cpp`. The installable font files are in `fonts/` and are generated by `tools/build_t12_font.py`.

## Firmware architecture

- `sequencer/src/main.cpp`: initialization and real-time main loop.
- `sequencer/src/hardware.cpp/.hpp`: GPIO, ADC, I2C, MPR121, OLED-facing inputs, PWM and RGB PIO output.
- `sequencer/src/engine.cpp/.hpp`: clock, sequence playback, CV, gate, slide, ratchet, vibrato and live-key overrides.
- `sequencer/src/model.cpp/.hpp`: `Project`, `Step`, `Settings`, scales and validation.
- `sequencer/src/ui.cpp/.hpp`: pages, menus, performance controls, editing and persistence triggers.
- `sequencer/src/storage.cpp/.hpp`: flash banks, project slots and settings persistence.
- `sequencer/src/display.cpp/.hpp` and `graphics.cpp`: OLED drawing.

## Data model

`Project` contains the recorded sequence, key-note assignments, scale, root, transpose, and loop window. The recorded sequence length must remain independent from the active loop window.

`Step` supports:

- key;
- rest/time;
- slide;
- vibrato;
- retrigger;
- ratchet;
- shift/accumulator behavior.

`Settings` contains clock mode, BPM, clock division, gate length, auxiliary mode, LED brightness, encoder direction, vibrato settings, CV calibration and performance sequence/arp directions.

## Performance behavior

When the sequence is running, turning the encoder selects a performance parameter. The `− / +` octave buttons modify the selected parameter:

1. Octave transpose
2. Sequence direction: forward, backward, random
3. Arp direction: up, down, up/down
4. Gate length: 10–90 % of the clock interval
5. Clock division: ×1, ×2, ×4, ×8
6. Loop length
7. Loop offset

Loop semantics:

- recorded sequence may contain up to 32 steps;
- loop length selects a window inside the recorded sequence;
- loop offset selects the start of that window;
- example: 32 recorded steps, loop length 8, offset 0 = steps 1–8;
- offset 8 = steps 9–16;
- offset 16 = steps 17–24.

Editing Keys, Steps or Calibration stops playback and puts the engine in an idle state. External clock edges are ignored while those pages are active.

## Clock and gate

External clock is active-low on GPIO3 with pull-up. Reset is active-low on GPIO6 with pull-up. Gate output is inverted at the hardware stage. The engine explicitly cancels the previous logical gate before retriggering.

The CV is written before the gate in the hardware update cycle. Gate duration is configurable from 10 % to 90 % of the current step interval.

## Slide behavior

`Step::glide` is intended to behave like a TB-303 slide:

- the next step changes the pitch target;
- the pitch interpolates toward the new note;
- no new gate retrigger is sent while the previous gate is still active.

## Persistence

Project slots and settings are stored in RP2040 flash. The storage header is versioned. Changing the storage structure requires either:

- a migration routine; or
- a deliberate storage version bump with default initialization.

The USB backup application can dump and restore project/settings data. Do not silently change the binary format without updating the USB protocol and migration behavior.

## Reverse-engineering history and confidence

The GPIO map was established from the DIY v20 assembly documentation, the Doboz UF2 reference, PCB photographs, continuity observations and diagnostic UF2s. Roles marked as confirmed were tested on the physical module with the OLED diagnostic display, MPR121 touch test, RGB test, encoder test, octave-button test or jack test.

The RP2040 is not an RP2350. The close-up marking is `RP2-B2`, consistent with RP2040 silicon.

The touch IC is confirmed as MPR121. It is connected by I2C on GPIO0/1/2 according to the diagnostic firmware and physical routing. The twelve touch pads are mapped in the logical key order used by the firmware, while the physical panel is a 4-column × 3-row grid. The physical key order is reversed in X/Y relative to the logical sequence numbering; this mapping must not be changed casually because RGB LEDs and touch electrodes use separate confirmed mappings.

The RGB chain is a one-wire addressable RGB chain controlled by PIO on GPIO2. Several timing/color modes were tested; the working mode produces the expected RGB colors and animations. The current logical-to-physical packet mapping is in `hardware.cpp`.

The OLED is not a touch screen. Its front-panel connector exposes GND, VCC, CLK, MOSI, RESET, DC and CS. The display controller is driven by the custom SPI code, not a generic Arduino display library.

The DAC hypothesis was rejected during testing. The CV outputs are generated by RP2040 PWM and shaped/amplified by the analog circuitry, including TL074 stages. The PWM carrier is intentionally ultrasonic in the current firmware. The output is measured after the analog conditioning stage, not directly at the RP2040 pin.

## Electrical output details

Pitch and Auxiliary outputs use 13-bit PWM. The PWM carrier is approximately 24.4 kHz with the current clock configuration. The analog stage inverts or scales the signal as observed during the hardware tests; calibration compensates the measured output response.

The requested pitch range is 0–8 V. Calibration is represented by five target points: 0, 2, 4, 6 and 8 V. Each output channel has calibration data. Coarse and fine adjustments are stored persistently. The calibration page can select Pitch or Auxiliary output.

Gate is not a DAC output. It is a digital output whose external hardware stage is inverted. The engine writes the logical gate state and `hardware::write()` applies the physical inversion.

## Input behavior

Clock and Reset are active-low conditioned Eurorack inputs. GPIO3 and GPIO6 are configured as inputs with internal pull-ups. A Pamela Workout trigger is expected to pull the input low. The first valid external clock edge establishes the phase origin and must produce the first sequence event; do not reintroduce a one-edge delay.

The encoder is quadrature decoded on GPIO11/12 and its push switch is GPIO10. Direction reversal is a persistent setting. Octave buttons are ADC GPIOs used as digital button inputs, with LEDs on GPIO21/22. Long encoder press changes page; normal click starts/stops where that page supports transport.

## MPR121 capacitance details

The MPR121 measures each pad by charging/discharging the electrode and observing the change caused by the finger’s capacitive coupling to ground and the surrounding electric field. The firmware reads touch status and filtered electrode values. Filtered values are not pressure sensors and should not be described as physical force; they are a proxy for contact/coupling strength.

Current CAP SENSE behavior maps the filtered value to Auxiliary CV and pad LED intensity. The correct future calibration model is per electrode:

```text
idle[k]      = filtered value with no finger
touch[k]     = filtered value with a normal touch
normalized   = clamp((value - idle[k]) / (touch[k] - idle[k]), 0, 1)
```

Calibration must reject invalid ranges, handle environmental drift and save the twelve baselines/ranges in Settings.

## Sequence editing and transport rules

The sequence has up to 32 recorded steps. A step can be a rest. Editing a key or step must stop transport. Calibration also stops transport. While these pages are active, external clock edges are ignored so the sequence cannot restart behind the user’s back.

Performance page behavior:

- click toggles play/stop;
- when stopped, `- / +` changes sequence transpose by octave;
- when running, encoder rotation selects a performance parameter;
- held `- / +` buttons repeat their adjustment after an initial delay;
- loop length and loop offset operate on the recorded sequence window;
- loop changes must not erase steps outside the active loop.

Live touch behavior during playback:

- one held key overrides the pitch selected at the next step;
- several held keys are cycled as an arp on successive steps;
- touching keys during playback does not call the immediate preview path;
- LEDs may show touch state, but playback must not create stale or shifted LED indications.

## Step parameter semantics

`SLIDE` is TB-303 style. A slide step is linked to the preceding sounding step: the pitch target changes and glides while the previous gate remains open, without a new gate retrigger when the prior gate is still active.

`RATCHET` creates multiple gate events inside the step. `RETRIGGER` repeats gate events according to the step timing. `VIBRATO` enables the pitch modulation for that step. `REST` suppresses the gate and clears the sounding state. `SHIFT` is the per-step accumulator/degree shift and must remain bounded.

The real-time order is deliberate:

1. process clock/reset and touch input;
2. calculate the step and target pitch;
3. write Pitch/Aux PWM;
4. write the inverted Gate state;
5. update OLED and LEDs at their slower UI cadence.

Flash writes must never occur while transport is running.

## Storage and USB backup

Flash storage uses versioned headers and redundant banks. Projects are stored in slots; Settings include calibration and performance settings. A storage version bump can cause old data to be ignored, so migration is required for future structure changes.

The companion application is in `t12-backup-web/`. It is an Electron macOS app using `serialport`. The protocol is line-oriented for commands and binary framed for backup data:

- `T12DUMP\n` requests a backup;
- `T12RESTORE <length>\n` begins restore;
- firmware sends `READY\n` before accepting restore payload;
- firmware sends `OK\n` after successful restore;
- the app writes/reads `.t12` files.

The app must close a serial port only when `port.isOpen` is true, clear timeout handles after completion and avoid closing the same port twice. The current fix is in `t12-backup-web/main.js`.

## Font project

The firmware bitmap font is a 5×7 glyph grid with a six-pixel normal advance. `tools/build_t12_font.py` generates installable TTF files with a 70-unit em square, where ten font units represent one logical pixel. Use sizes 7, 14, 21, 28… for integer pixel scaling.

Supported glyph groups include uppercase, lowercase, digits, ASCII punctuation, arrows and geometric symbols. Figma may still apply anti-aliasing; use integer multiples of 7 px and disable smoothing where possible.

## Known risks when changing code

- Changing `Project` or `Settings` layout requires a storage version/migration decision.
- Changing OLED column offsets can recreate the two-column right-edge artifact.
- Changing key/LED mapping can make valid touches appear on the wrong RGB pad.
- Changing gate polarity can reintroduce the large timing/latency symptom previously observed.
- Adding expensive OLED rendering or flash writes inside the clock path can reintroduce timing errors.
- `p.length` is the recorded sequence length; `loopLength` and `loopOffset` are the active playback window and must remain separate.

## Important working rule

Before editing, inspect the current source and the latest UF2/build state. Do not infer that an older version still matches the current behavior; this project has many iterative UF2 builds.
